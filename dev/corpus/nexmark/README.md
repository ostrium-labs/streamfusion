# Nexmark cases (preview)

The 23 Nexmark queries q0 to q22 of
[nexmark/nexmark](https://github.com/nexmark/nexmark) (commit
`6b3646c3baec701f1fa74baf938d235f742e5d3c`, Apache-2.0; see `NOTICE`) as
cases for the differential harness (`native/loams-stream-conformance`, case
format in `src/case.rs`, how to run in `dev/oracle/README.md`).

**Status: not yet run end to end.** No `expected.jsonl` is recorded yet: the
cases have not been run on the Flink 2.2.1 oracle, and Loams Stream does not
answer the SQL Gateway yet, so none has run on Loams Stream either. The test
`the_nexmark_cases_load` only checks that every case loads and passes the
harness's source rules.

```text
dev/corpus/nexmark/
  NOTICE, README.md
  vendor/LICENSE                 upstream's licence
  vendor/queries/                ddl_gen.sql, ddl_views.sql, q0.sql ... q22.sql, verbatim
  data/                          the shared dataset (one copy)

  q0/ ... q22/                   one case per query

    data -> ../data              a symlink to the shared dataset
```

## The data

Generated by `loams-stream-oracle nexmark-gen`, a Rust port of upstream's
event generator (`native/loams-stream-conformance/src/nexmark.rs`), from the
repository root:

```sh
cd native && cargo build -p loams-stream-conformance && cd ..
ORACLE=<cargo target dir>/debug/loams-stream-oracle
$ORACLE nexmark-gen --events 3000 --seed 0 --rate 50 \
  --base-time-ms 1767254370000 --side-input 10000 --out gen
for t in person auction bid; do mv gen/$t.json dev/corpus/nexmark/data/$t/; done
mv gen/side_input.csv dev/corpus/nexmark/data/side_input/ && rmdir gen
```

That is 3000 events (60 persons, 180 auctions, 2760 bids: upstream's 1 : 3 :
46), one every 20 ms of event time (`first-event.rate` 50/s instead of
upstream's 10 000/s, so the 60 s of data span six 10 s windows), from
2026-01-01 07:59:30.000 UTC (so `HOUR(dateTime)` in q14 takes the values 7
and 8), and q13's side input of 10 000 lines `i,i` (upstream's
`SideInputGenerator -n 10000`). About 940 KB. The test
`the_shared_nexmark_dataset_is_reproducible` regenerates it and fails if the
shipped files differ.

`nexmark-gen` options: `--events N` (required), `--seed S` (default 0),
`--out DIR` (default `.`), `--base-time-ms T` (default 1767225600000,
2026-01-01T00:00:00Z), `--rate R` (`first-event.rate`, default 10000),
`--side-input ROWS` (also write `side_input.csv`). Files are JSON lines with
upstream's column names; timestamps are in Flink `json`'s default SQL format
`yyyy-MM-dd HH:mm:ss.SSS`.

How the port relates to upstream: ids, proportions, field derivation and the
order and bounds of every random draw are upstream's. Upstream draws from an
unseeded `SplittableRandom` and takes its base time from the wall clock, so
its events differ on every run and cannot be reproduced; the port seeds a
`java.util.Random` per event with the event id (Apache Beam's Nexmark
scheme, which upstream derives from) and takes the base time as an option.
`--seed` perturbs every seed; `--seed 0` is the Beam scheme. Upstream
quirks are kept: a bid's bidder gets `+1000` twice (bidder ids start at
2000 and so rarely match a person id), the hot seller (person 1000) is
never generated (the first person is 1001), and email addresses may hold
spaces.

## The cases

Common to every case:

- **Sources.** Upstream reads one `nexmark` connector table (`ddl_gen.sql`)
  through the views `person`, `auction` and `bid` (`ddl_views.sql`). Here
  they are three `filesystem` tables in `json` format on
  `${CASE_DIR}/person`, `/auction` and `/bid`, with upstream's columns and
  types and the watermark `dateTime - INTERVAL '4' SECOND` that upstream
  defines on the single table. Difference: each table has its own watermark
  instead of one shared by the three event types. The input is bounded and
  each file is in event-time order, so no event is late either way.
- **Sinks.** Upstream's `nexmark_qN` tables write to `blackhole`. Here the
  same columns go to a `filesystem` table in `debezium-json` under
  `${SINK_DIR}/nexmark_qN` (`collect = "sink"`), so the changelog survives.
- **Queries.** `query.sql` is upstream's `INSERT` verbatim, with upstream's
  description comment, except where listed below.
- **Rules.** `mode = "streaming"`, `order_sensitive = false` everywhere.
  Insert-only results are `changelog_significant = true`. Results with
  retractions (aggregates and Top-N over unbounded input, joins feeding
  them) depend on how the inputs interleave, so they are
  `changelog_significant = false`, folded by the key listed below, or by the
  whole row (q5, q6).
- **Data.** The case format copies a case's own `data/` directory, so each
  case's `data` is a symlink to `../data`; the runner follows it unchanged.
